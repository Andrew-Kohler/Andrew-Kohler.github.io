About the Project

OddQuatic is a mobile MMO, where each user keeps fish that swim across the ocean. If you see a fish, it's because another user is online. See the vast variety of fish, create your own, interact with each other via your fish, and combine your fish with others' to truly turn the ocean into a place most Odd.

I'm developing OddQuatic to launch on iOS and Android, using the project as an opportunity to learn about the mobile development lifecycle as well as networking and database backends in games. The contents of this devlog include progress updates, explorations of my technical decision making, and deep dives (pun intended) into architectural choices and processes.

First Post - Project Introduction

8/26/26

And so we begin!

I'll be aiming to update this log frequently over the next few months as development on this project really gets underway. My first order of business is to explore the technologies I think I want to use - Unity, Unity Online Services, and MongoDB - and examine them to see if they're really the best fit for this project and its needs, or if my prototype should transition to different platforms.

A little bit about the project itself, though, before taking the time to outline technical needs. My initial interest in OddQuatic as a project was the idea of a shared fish tank - users could open their installation of the game, and be greeted by not only their fish, but the fish of others. The foundation of this game is fish swimming from left to right across the screen, and at the right screen boundary, they're just swimming into someone else's tank from the left. When players are online, their fish are online, so seeing unfamiliar fish is a sign that you're not alone. That's where "MMO" comes from in the initial description - massive might be a stretch, but this is a multiplayer online aquarium.

I'm also interested in making use of and learning about databases. Right now, I can't tell you the difference between SQL and NoSQL, but I know it's important! More than just learning about them, though, OddQuatic's mechanics involve times where an online user will need a reference to an offline user's fish, and the game will need to modify that fish so that the changes exist when the latter user logs back on. You might have noticed my choice of noun in "user" as well; people switch phones all the time, so currently included in the scope of this project is a very basic account system.

Local storage of data would potentially be practical without those two considerations, but a database storage system not only accounts for what I want to do right now, it's futureproofing for other online or connectivity based mechanics involving multiple users. There's an extra labor cost involved in setting up a database compared to a local text file, of course, but I place the ability to create unique online interactions as something worth the time cost.

Finally, I do want to ship this project to mobile platforms. Having easy access to a global aquarium and being able to casually make a fish or see if any friends are passing by, or lining up your phones to watch your fish cross each other's screens, are ideas that have had a glowing reception by my similarly-aged coworkers that make up part of my target audience.

The technical needs that my toolkit needs to meet based off of that description, then, are as follows:

  • I need to be able to access an always-online storage system. I need to use this storage system to look up, and emplace, objects with unique ID's and other distinguishing information rapidly. The order of my data is irrelevant to gameplay; speed is the priority in both reading and writing, so I want a solution that's fast.
  • That storage system should also be reliable. Being able to load fish into the game, and create new ones, are tasks that are fundamental to my gameplay loop, and if performing those actions has a significant error rate, the game isn't fun.
  • I need to be able to send requests between clients and a server. There isn't a need for pinpoint realtime accuracy, like a fighting game, but a gap of a few seconds between one player sending a server request and another player receiving the result of it from the server is desirable for the intended gameplay.
  • Again, the method of networking should be reliable; this game relies heavily on players being "always online".
  • I need to develop in an environment that makes mobile development, testing, and deployment relatively simple. Low iteration times will be essential to network tests early on, and a platform that has options or documentation on performance optimization for mobile would be excellent. (Anything can be optimized for mobile, but as someone new to the practice, I'd appreciate some help.)

As a final note, there are other gameplay elements that I'll be getting into as this blog continues that weren't brought up here, but for my purposes right now, all premade engines generally have equal capabilities in that regard. Thanks for reading my first log - sea you next time!

- Andrew

Choosing An Engine Based On My Criteria - Networking

8/27/26

Ah, the question every developer must face. What will I use to make my game?

Firstly, I'll establish some ground rules that I'm following to make this question a little less intimidating. I plan on using a commercially available game engine. An entirely custom solution would be DRAMATICALLY educational, but I want to be able to ship this project in 4-6 months with a first version, and in my personal experience, even a guided construction of a well-made game engine takes 4-6 months on its own. I'm considering Unity 6, Unreal 5, and Godot, as they're commonly known and used across the games industry, the field I find myself in.

I've used Unity to create an initial prototype, and have extensive familiarity with it, but on the verge of starting this project in full, I'd like to conduct some further analysis. I'll be evaluating each of my choices by the following critera, based on my needs in the first post:

  • How well suited are the engine's networking capabilities to handle simple client-server relations at scale?
  • What features does the engine provide that are targeted to mobile development?
  • What integrations exist between the engine and common database backends?

By common database backends, I'm referring to PostgreSQL and MongoDB, which some databases research (coming in full soon) has highlighted as the most common SQL and NoSQL solutions respectively, both with virtues for game development. I'm still missing some context as to how these databases are hosted, as all of the prototype work I've done with MongoDB has been through a local host, but for now, I at least understand that there needs to exist (a) a database, (b) a server via which to access that database, and (c) a game to do the accessing. Let's get to it!

Networking

Unity

Unity's official page for their networking services is impressive. They offer pre-existing packages for social components like friending users as well as different packages geared towards casual, fast-paced competitive, and event-driven/idle multiplayer games. On closer inspection, the event-driven module (Cloud Code) appears to be more geared towards live game updates and, appropriately, using code that's on the cloud, so perhaps not exactly what I'm looking for. I moved to Unity Online Services and found an extensive list of products; they have solutions for player accounts and management, analytics, cloud saves, pretty much anything I could ever need. If I were making this game purely to get it out the door as quickly as possible, I would entirely use their pre-existing solutions; they're well documented with transparent pricing and capabilities.

However, I'm pursuing a custom solution, trading that safety and convenience for flexibility and a better understanding of what's under the hood. My research eventually led me to a more general resource that filled in some gaps for me:

  • The 4 main areas of concern in any multiplayer game are the runtime, transport, backend, and fleet. The runtime is the game itself, the transport is the layer that communicates between runtimes, the backend is the server supporting communication, and the fleet is the collection of servers we may use to host the game
  • There's a difference between peer to peer (direct - everyone connected to everyone else) and peer to peer (client server - one player is a host)
  • I'm pursuing a dedicated server model
  • There are lots of options to support dedicated servers - Amazon GameLift, Azure PlayFab, GCP
  • PlayFab has robust player account support
  • Each of the above services offer managed database options

So, the nature of this project has veered somewhat into understanding how major commercial server services and their database integrations work. Returning to engine analysis, though, the rest of the video series I cited and the documentation on all of these servers gives me confidence that Unity can interface with a dedicated server in a way I'll be able to understand. Unity does not offer a service as a company to host dedicated servers, but their platform fully supports making a "Dedicated Server" build with no graphics or audio to live on the server as the host. It would take a little legwork, but I expected nothing less.

There are also several plugins that appear to handle many of the API needs for a database specifically. I'll keep them in mind! As well, I found a very cool portfolio piece of someone's with them making a server themselves from scratch and integrating it with Unity. I do not know anywhere near enough about servers to parse it, but I'm saving it here for future education.

  • Unity official multiplayer page
  • Multiplayer game architecture in Unity
  • Example of a 3rd party service for dedicated servers
  • Database plugin
  • Custom server

Unreal

Knowing now that the keyword "dedicated server" will be practical to me, looking up how to make an Unreal game with a dedicated server provided me with an Epic-made tutorial. Wonderful!

However, just a little more research reveals that to make a Dedicated Server build, I need a source copy of the engine, not the precompiled binaries. This isn't prohibitive, I currently have the ability to requisition the hardware space for it, but it is a long, error prone step.

My second source also has some fantastic explanations of the different dedicated server options availible to me.

  • Self managed orchestration services give full control to me over server scaling, allocation, and checkups - great for something with very specific needs (example service - Kubernetes)
  • Managed game-server hosting is where those services I listed earlier fall into - the platform will handle scaling and placement, and I do a lot less management but give up a lot of control
  • Game-specific hosting provides like Gameye spin up a server on request, kind of like P2P client/server with the "host" just being the service instead of a player

With my question answered (yes, it's possible and supported), I'll be checking the box and moving on. Like Unity, Unreal also does not offer an internal server system, but has several utilities for online functionality like accounts, player data storage, and lobbies.

  • Epic's documentation on dedicated server setup
  • Information on online dedicated server setup
  • Epic Online Services

Godot

Again, knowing what to look up has made this pretty simple. Godot supports networking/multiplayer and a dedicated server architecture. Between all three of these, it doesn't really look like there's a clear winner; they all have their unique networking systems that will need code, and all of them support a connection with a dedicated server.

  • Godot dedicated server docs
  • Dedicated server full tutorial

So, is there a winner? In my books, not yet. Each engine provides the functionality and integration I need, and there's not a lot of diversity in the ways they provide it. This hasn't altered my initial choice of Unity yet, a decision currently motivated by the next criteria I need to analyze: practicality for mobile development.

I realized a little ways into writing about Unity's multiplayer capabilities that this is a multi-day, multi-post affair. See you next time for looking at each engine's mobile development capabilities!

- Andrew

Choosing An Engine Based On My Criteria - Mobile

8/27/26

The journey continues! Let's dive into each platform's support for mobile developers and see what they have to offer. As a referesher, the question I want to answer for each of these platforms is "What features does the engine provide that are targeted to mobile development?"

Mobile Development

Unity

Unity is off to a strong start based on its landing page for mobile developers alone. Company-made tutorials for mobile development, live operations, growth and monetization, the whole 9 yards. I will do my best to be more than a hapless consumer, though, and dig a little deeper.

Many of the LiveOps services Unity offers tie directly back to their networking services, but additionally, they have documentation and support for things like in app purchases, push notifications, and a variety of analytics. It's all very impressive, for sure.

I'm far from the first person to conduct an alaysis like this as well, so my next step was to see what other users are saying. What I found seems to support the company line - Unity excels at performing well on a large range of devices, and has tools targeted specifically for mobile optimization. The common detriments to using it to mobile dev are a lack of advanced tools and ability to create high-fidelity experiences with complicated 3D graphics. As someone using pixel art, neither of these things really worry me.

I'm already at a point where I feel my question is answered for Unity, but I'll go one step further and interrogate what exactly these performance tools are. I quite enjoy learning about that sort of thing. It seems that most of the tools availible are just permutations of Unity's profiling systems, but that's honestly good enough; not having to fight a PC-only tool to show me information about a phone seems like a big advantage. I also found a lot of potential optimization techniques with examples, but with premature optimization being the root of all evil, I'll save those for, at the earliest, having a game to even optimize.

I know literally nothing about Godot mobile development, especially compared to my starter knowledge of the other two engines. Let's change that.

It's immediately revealing that every resource for this process is unofficial. Godot is open source, but unlike UE and Unity, there is no central documentation for the basics of mobile gamemaking. The Godot subreddit has a fair few posts on the matter, and there's scattered third party documentation, like the one I linked below for getting set up for Android, but that's about it.

Looking for more recent sources, I found a fellow independent developer's devlog. They discuss how they've been making a mobiel game for Godot 3, and in the process of porting it to Godot 4, encountered unforeseen and hard-to-debug performance issues. While I'd be making a 2D game, the light they shone on how this issue has been underreported and not addressed well makes me wary of Godot for mobile at this time.

With enough documentation to potentially make an app on all 3 platforms, the true test here would be to dedicate a week of development to doing just that; making the simplest interactive application possible to test out workflows, adding in a tutorial-adherent or tutorial-like version of a feature I want for my app, like maybe trying out an IAP implementation. With potential for functionality everywhere, the next test becomes usability, and what's possible to achieve realistically rather than as advertised. However, I don't have the resources for that at my team size (1) and my development time (4 months), so this search process will have to be the extent of the decision making process.

Currently, my thought process is this. I have familiarity with Unreal and Unity, which is enough for me to rule out Godot. "Learning Godot" is an additional 4-6 month process to do it properly, and as it's also currently the worst option for mobile development in terms of documentation and viability. I'm leaning towards Unity at the moment just due to the growing overhead that Unreal represents - not only would I need a source build, but the systems that enable Unreal to produce AAA visuals would in opposition to my simple 2D art goals, not helping them move along.

For the final part of this evaluation process, it's clear that the question I need to ask has shifted from "What integrations exist between the engine and common database backends?" to "What would the process be for using a dedicated server to connect players and host a database?" My initial prototyping on this project was using Unity, MongoDB, and a local server thrown up by a bit of Node.js inbetweening. But with an always-online game, that local server becomes online and dedicated.

There is still the question of SQL vs NoSQL that needs some further interrogation as well, so I'll be trying to answer those two questions in my next post. The field is narrowed to 2; now to get it down to 1!

Choosing An Engine Based On My Criteria - Servers and Databases

8/31/26

This is gonna take the day, I can feel it in my bones. Let's get started.

Databases

Server and database determination are somewhat separate in my eyes. While of course the server side of things will need a clear pathway to access / hold the database, we live in an age of great abundance. The fact that I'm using a prebuilt, managed cloud server fleet abstracts away some of the problems I would face if I wanted to hook up a custom server running off a PC under my desk. One should always validate their assumptions, though - I want to make the choice between SQL and NoSQL first, and then look at my server options from the perspective of needing to connect both a game and a database. I'm currently standing by the choice of either MongoDB or PostgreSQL; they're popular, commonly used, and have been recommended to me in a games context during my research. I'm also curious about what those under-the-desk problems might look like, so hopefully during my server research I can point some fingers at where I might run into trouble making moonshine.

So, what have I learned about the difference between SQL and NoSQL? Well, I find it very funny that "NoSQL" stands for "Not Only SQL." But more than that:

SQL (Relational)

  • Data is organized into tables made up of rows and columns, or in the vernacular, records and fields. An example might be a record corresponding to a UID, and within the record, a variety of a specific player's data is accessible in fields.
  • The structure of records and fields is defined by schema - blueprints that we define for how data should be stored.
  • SQL databases scale vertically: more storage availible equates to more capacity.

NoSQL

  • NoSQL databases, at a very high level, are best for unstructured or semistructured data. Text, images, videos, sensor data - things of non-uniform scale or format that need to be collected but might require an inefficient amount of schema to put into boxes.
  • There are subtypes of NoSQL databases; for example, my prototype used a document database, storing data as JSON-like documents. Other types are key-value storage, like a big online map; column-based, best for analytics data; and graph databases, storing nodes and the relationships between them.
  • NoSQL databases scale horizontally: higher workloads can be supplemented with additional servers. It's the difference between beefing up one server with additional specs (vertical) and adding more servers to efficiently distribute the work.

This really is just choosing the best data structure for the job on a massive, project-defining scale, isn't it?

Taking a look at my use case, my data should be very structured. The things that define a fish shouldn't be dynamic in gameplay; while fish might become more complex as I update the game, users won't be submitting or saving fish with a variable number of properties. I could define a fish schema, and always know how to access a fish. The same follows for users. Would a user have-a fish or a fish array? How object oriented can a relational database be? I suppose it's comparable to an inventory system, which I do have an example of thanks to a Generalist Programmer source. Here, the inventory uses a separate schema, but is able to reference the player ID so that both the player and their inventory can be searched for using that same value. That makes a lot of sense to me.

Also introduced to me is the idea of polyglot persistence: using multiple databases in the same project so that everything is used for its optimal purpose. For me, this might take the form of using some of Unity Online Services' data management? I'll start with the one database I know I need and go from there.

After reading over multiple sources, it seems like I can't necessarily go wrong, so here's a list of factors that I'm basing my decision on.

  • SQL databases enforce structure, while NoSQL allow for rapid unstructured iteration and flexibility at the cost of having to pay more manual attention to your data.
  • PostgreSQL helps greatly with ensuring transactions are atomic (remembering my ACID principles I read about). That's potentially important to me as I plan and scope for player to player communication and exchange!
  • SQL predates NoSQL in terms of documentation and community, although its history and age do make it a little less intuitive.
  • For games, SQL has been recommended to me for things with a known structure like player accounts and inventories, while NoSQL works better for iterative or semistructured data like player progression and achievements.
  • Speed is something of an abstract figure. From what I can tell, more queries may be required to retrieve data in a relational database, whereas just being able to pull up a JSON file by ID with everything in it that you need in a NoSQL context is, relatively, faster. However, in measures and estimates I could find, NoSQL comes out to about 2x as fast as SQL, but both query times fall within the space of 2 or 3 frames of a 60 FPS game. That might be impactful if rapid retrieval impacted fast-paced gameplay, but for my purposes, both are well within desired limits.
  • Popular usage appears to be split right down the middle. Fortnite uses NoSQL for player saves, some major MMOs use SQL, and everyone has a favorite. The best advice I've seen is to go with what your team has experience in.

With all that said, I want to try using an SQL database, so welcome to the team PostgreSQL! This is a choice motivated by wanting to have a well-defined structure for player data that's hard for me to break, and relational data being a good fit in general for the player and fish centric data I need to store. While this is a topic that could make up an even deeper dive (what about SQLite? Firebase?), I also want to be conscious of the fact that I'm here to learn. Getting a working knowledge of one part of this vast topic will allow me to better assess the relative costs and benefits based on my own knowledge as an engineer - so let's get learning!

Servers

Alright. I need to find a server that meets the following criteria:

  • Can serve as host for a multiplayer game and accomodate a large number of users
  • Has support/documentation for SQL database integration
  • Has other documented usership for mobile game developers
  • Won't break the bank of a solo graduate developer

This is an instance where I'm not going to balk at the tried and true, so I'll be doing a comparative analysis of 3 of gaming's largest server providers and corporations in general. Amazon GameLift, Azure PlayFab, and Google Cloud Platform will be the options, and one will emerge victorious. I found a pretty cohesive source comparing each service on a lot of fronts, and the general impression is that that first bullet point is pretty much a moot comparision. The services, respectively, play host to Fortnite, Rainbow Six Siege, and Pokemon Go, so I don't think a scrappy indie mobile game will make too much of a dent. The other three points, though, are definitely worth some independent journalism.

Amazon Gamelift

  • Database x Game: The Amazon Relational Database Service appears to be more or less what I'm looking for. Something I'm unclear about with every option is how the game accesses the database on the server for information, but at least here things are under the same roof. Based on my prototyping where I used Node.js to spin up a local server, my current theory is that a similar script to the one I wrote will be placed on the server and run during bootup, spinning up the database for access. Here, let's do a little diagramming. This is my understanding, generally, of how this pipeline might work. I am so excited to correct it as I learn more, but you gotta start somewhere! Anyhow, a service designed for databases under the same roof as what's hosting my game is enough for me, for now.
  • Mobile Support: Short answer, yes! This felt like something of a moot question as well, since the differences between a mobile and PC game come mostly with the game itself, but I wanted to check. I'm glad I did; I found this official Amazon diagram for how their GameLift service works at a high level in the documentation (which seems decent). It looks like my database would fall under backend services?
  • Cost: AWS offers a free tier with $100 in credits off the bat, $100 more for various usage incentives, and will keep the account open for 6 months or until credits run out. That's more than enough to tinker with! This free tier also gives access to RDS, which is perfect.
  • Other: Third party analysis notes a steep learning curve as part of the price here. I found engineer-oriented tutorials on YouTube for getting up and running in Unity and Unreal, which I take as a good sign, but I'll keep an eye on accessibility of the other platforms.

Azure PlayFab

  • Database x Game: Azure lets me do this: It's rather accessible and compelling, just being able to click around a little and make a new one of these. And what's more compelling? I can host a database, and the Azure ecosystem will take care of me. Beautiful.
  • Mobile Support: Right on the front page, explicit note of support for App Store and Google Play, as well as SDK's for Unreal and Unity. Looking into the documentation, Android and iOS development are essentially just supported via these SDKs. Wonderful, excellent, moving on.
  • Cost: PlayFab lists out a lot of prices for a lot of different things up front, but most importantly, they have a free tier with "Development Mode" - essentially allowing infinite tinkering within some usage bounds (under 1,000 player accounts created). The free tier allows for a lot of uptime without charge even outside of development mode, about a month's worth. The full monthly breakdown after I'm off the freebie list comes out to about $75, though, the vast majority of that coming out of compute costs rather than network usage with my small estimates. I'm actually not sure if Amazon eats those compute costs themselves or if there's fine print I'm not seeing and my under-a-dollar calculations are purely network costs.
  • Other: Accessibility looks great - documentation, tutorials, and so on. Unsurprisingly, Microsoft and XBox want people in their ecosystem; I wouldn't be shocked if the 'Everything Is An XBOX' initiative actually helped push the accessibility of this service forwards. But I digress.

Google Cloud Platform

  • Database x Game: GCP offers a managed relational database service on the cloud; wonderful. However, the offered documentation is sparse as far as any information about potential connectivity to any kind of gaming ecosystem at all. The splash page looks like it should have some useful redirects for this sort of documentation, but it's dominated by AI advertisements. Buried in that content, though, I did eventually find a link to a page specializing in databases for games with Google Cloud. It's nice, and offers some tutorials for how to use Spanner, their managed relational database solution, but as soon as I look deeper into the documentation, I again find myself in a landscape not specialized for gaming. It's clear the possibility exists, but I'd have to do some figuring. Gaming isn't even a major header category in the docs.
  • Mobile Support: Niantic used GCP for Pokemon Go, so I know the intergration I'm looking for is entirely possible. Google's documentation, though, seems to focus on mobile development in the traditional sense, which doesn't highlight a lot of terminology I'm familiar with. It looks like it's very Firebase focused as well. Again, an instance where I could definitely puzzle things out, but the documentation just isn't as suited to my use case.
  • Cost: Google's free trial is $300 in credit over 90 days. It looks like my monthly costs would be somewhere in the realm of $20, which isn't horrible, but that grace period is pretty slim.
  • Other: I'm just really not enamoured with the idea of using this documentation. GCP can do games, but it doesn't look like the starter playplace that will accelerate learning the fundamentals.

So, where does that leave us? I think now I can say.

  • Engine: Unity 6 LTS. Unity's lightweight development environment, focus on mobile support, and extensive documentation match my needs on this project. A 2D pixel art style doesn't need Unreal's amazing feature set and build times, and without the need for AAA visuals, Unity's mobile support comes out on top.
  • Server: Azure Playfab. While the pricing might get a little hairy down the line, the option to keep a game in development mode for an unlimited time, combined with easy linkage to Azure's database services, means actual development won't be impeded by financial logistics. Additionally, the documentation and support ecosystem was my favorite of the three, being the most oriented to my use case of making video games.
  • Database: SQL, specifically PostgreSQL if I can. The structured schema of a relational database are an excellent match for my game, wherein the entire development scope for the next 4 months doesn't include anything that can't be broken down into an unchanging format. This structure will help me prevent formatting mistakes and keep data organized and well-maintained.
